# 可选 AI 验收规划

默认的 `donegauge review` 完全在本地工作。需要帮助拆分一条复合需求或为已有测试找关联时，才使用 `--ai`。模型看不到断言正文，不能仅凭测试名证明需求已覆盖。

## 1. 配置提供方

在自己的终端或凭据管理器设置以下环境变量，不要把密钥写入项目或贴在命令行参数中。

| 变量                      | 用途                                                                                                                                                                                                   |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `DONEGAUGE_PLANNER_MODEL` | 账号或本地服务实际可用的模型名称；没有默认值。                                                                                                                                                         |
| `DONEGAUGE_PLANNER_URL`   | 完整 Chat Completions 地址，默认 `https://api.deepseek.com/chat/completions`。兼容服务需支持非流式 [JSON Output](https://api-docs.deepseek.com/guides/json_mode/)。仅回环地址允许 HTTP，不跟随重定向。 |
| `DONEGAUGE_PLANNER_KEY`   | 仅用于向上面的地址传递 Bearer 凭据；远程服务必需，本地服务可省略。切换提供方时请更换或清空此变量，避免把同一密钥交给不同服务。不会显示在预览或传给测试子进程。                                         |

## 2. 先看披露内容，再决定是否发送

以已安装的 CLI 为例。以下编号和摘要均来自前一步的实际输出。

```sh
donegauge review --ai --task '注册后能登录，弱密码要展示原因' --json
donegauge review --ai --draft DRAFT_ID --send SEND_DIGEST --json
```

第一步默认**零模型请求**。检查 `endpoint` 和 `body`：请求包含固定提示、未绑定且未锁定的需求，以及最多 40 个候选测试的名称和编号。不单独读取或发送源码、命令、diff、文件路径、对话或运行日志。需求和测试名本身可能含敏感信息。可换成脱敏需求，或在两步都加 `--omit-tests` 只分享需求。改变地址、模型、内容或草稿后须重新预览。交互模式按回车表示不发送。远程调用可能计费；单次 30 秒超时、不自动重试。

第二步只请求建议。成功返回新草稿号，原草稿原样保留。查看每项的原文、拟议条件、理由、候选位置和待澄清的问题；未被模型提及的条件保留，已有绑定、交互编辑过的条件和排除项不参与改写。无法确认关联时可以改为人工。未知候选、命令字段、状态字段、格式错误或不完整的回复会被拒绝，不部分采纳。无模型配置、无凭据、超时或无效回复时输出原草稿与原因。自动化请检查 `kind`、`planner` 和 `notice`，不要把成功预览当作模型成功或验收通过。

任一规划请求都不会运行测试。重新打开新草稿，才进入执行审阅：

```sh
donegauge review --draft NEW_DRAFT_ID
```

输入 `edit` 可调整，输入 `run` 才执行。非交互时使用新草稿的执行摘要和 `--approve`；发送摘要和执行摘要不通用。如果预览中出现需要澄清的问题，先明确需求或保留人工项。原 v1 验收配置、报告和 DSH 工具的执行权限不变。

## 3. 验证建议质量，不用模拟结果代替成绩

在源码仓库先运行 `npm run build`，再配置模型。下面的评测使用注册、购物车两个公开示例，每个 10 个标注任务，包含相似但没有对应断言的要求。每组后 3 项为留出集。默认只打印 **20 个请求的完整披露及批次摘要**，不联系模型。

```sh
node scripts/evaluate-planner.mjs
node scripts/evaluate-planner.mjs --send BATCH_DIGEST
```

第二条会对已预览的服务顺序发送最多 20 个请求，可能收费。只在同意后使用，不在 CI 中调用。分别看开发集和留出集：相关绑定数／全部绑定数、符合预期选择的任务数／任务数、不应有测试却给出绑定的数量。零绑定时精确率不可计算，不算 100%。还需人工对照每条原文和拟议条件，记录是否遗漏或缩窄行为；自动计数不能替代语义评审。模型、提示或标签变更后应重跑，并使用新的独立任务确认泛化。当前不宣称达到 PRD 的 90% 指标。
