# DoneGauge 产品需求文档：从一句需求到一份可信的验收报告

**状态：** 产品评审稿，2026-11-19。本文是基于 V0.1 的下一轮产品设计，不是已发布功能说明。下文的交互、命令和指标，除「现状」列外，均为提案。

**产品承诺：** 把原始需求交给 DoneGauge。执行前，你能看见准备检查什么、为什么选这些测试、还漏了什么；执行后，你能看见哪些行为有证据、哪些还不能确认。是否接受交付，由你决定。

**本轮最重要的取舍：** 把「手写配置才能开始」改成「先看懂一份可编辑的计划」。保留现有确定性执行器；不让模型接管命令执行、结果判定或最终签收。

**实现进度：** 本地 CLI 已有第一条 `review` 路径：静态查找 Node／Python 具名测试、规则建议、草稿编辑、摘要确认和真实 JUnit 报告。以下表格保留设计时的基线；AI 规划、DSH 引导式确认及用户走查指标仍是后续目标。实际入口见[中文版使用说明](../README.zh-CN.md#不写配置从需求开始)。

## 1. 为谁解决什么问题

| 用户与场景                                        | 真正要完成的事                                         | 新体验的成功信号                                         |
| ------------------------------------------------- | ------------------------------------------------------ | -------------------------------------------------------- |
| 不熟悉测试的个人开发者，刚收到 Agent 的「完成了」 | 知道自己的每条要求有没有被查，而不是弄懂如何写测试配置 | 不打开 JSON，也能指出哪条要求仍需人工检查                |
| 在 DSH 开发的独立开发者                           | 在当前对话完成验收，不必重复粘贴需求或查找日志         | 从结果卡能打开同一次运行的证据，或复制一段准确的返工说明 |
| 维护现有 CLI 配置的开发者                         | 保留可审阅、可重复、无需模型的执行方式                 | 不迁移配置，不开通模型，不改变已有自动化的退出码         |

首发只把 Node.js 和 Python 两条路径做好。首要指标是用户能否作出**正确的交付判断**，不是生成多少条条件、运行多少条命令，或报告里有多少绿色对勾。

## 3. 用户旅程：一次发起，一次执行确认

### 第一步：说清这次要验收什么

拟新增 `donegauge review`。用户运行后可粘贴需求，也可显式选择一份本地需求文件。在 DSH 里说「验收刚才的注册功能」，若宿主能提供用户选定的原始消息，就先展示引用的原文；拿不到就请用户粘贴。**不把 Agent 的完成总结当作需求，也不默读整段会话。** 熟练用户仍可直接使用现有 `check`。

随后只读查找项目清单、变更范围和相关测试。没有测试也进入下一步；没有需求则不猜，只问「你原本希望用户能做什么？」。Git 不可用时可整理需求草稿，但明确提示不能执行本产品的带快照验收。

### 第二步：在一屏内看懂并修改计划

以仓库的注册示例为基础，假设用户又提出了「弱密码时给出清晰提示」。以下是**执行前**应看到的内容，不是测试结果：

| 你的要求         | 准备怎么查                                       | 为什么这样选／还有什么不确定                                                                       |
| ---------------- | ------------------------------------------------ | -------------------------------------------------------------------------------------------------- |
| 邮箱不能重复     | 关联 `duplicate email is rejected`               | 测试实际尝试了带空格和不同大小写的第二次注册，并检查账户数仍是 1                                   |
| 密码不能明文保存 | 建议关联 `password is hashed with per-user salt` | 它检查带盐哈希和记录里没有明文，不证明整个身份系统安全。如果原话是「加密」，先确认是否接受这个解释 |
| 注册后能登录     | 关联 `login after registration`                  | 测试覆盖正确及错误密码；不覆盖真实浏览器或部署环境的登录                                           |
| 弱密码有清晰提示 | 待人工核对                                       | 当前示例测试没有断言提示文案。保留为缺口，不拿错误密码登录测试代替                                 |

首屏提示：「4 项要求，3 项找到候选测试，1 项待人工核对。还没有运行任何检查。」主操作为「确认并运行 3 项」，次操作为「调整计划」「仅保存草稿」。展开可看原文出处、测试位置、实际参数和工作目录。即使没有可运行检查，也可保存缺口清单；此时不显示「确认并运行 0 项」。

### 第三步：只打断用户做真正需要的决定

用户可以改条件、换测试、补一条、排除一条，或把存疑项留给人工。确认页显示这次会运行哪些程序、在哪个目录运行、会留下哪些文件。**同一份计划一次执行许可，不按验收项反复询问。** 修改后尚未执行的旧批准立即失效；用户可只保存，不会顺带启动测试。若选用远程模型，发送材料的知情同意发生在发送前，与执行许可是两件事。

### 第四步：先看决定，再按需看证据

示意（不是实际运行记录）：「**建议暂不接受整项交付。** 4 项要求中，3 项有通过证据；弱密码提示还没验证。」用户可选「查看 3 项证据」「查看人工检查步骤」「复制给开发 Agent」。不要让用户从几十行绿色日志里自己猜出还缺什么。

若登录用例明确失败，返工摘要应写：「要求：注册后可用正确密码登录。实际：目标用例未通过。请检查登录行为，修复后重新验收。」附本次运行与证据编号，不猜根因、不自动发送。若只是缺解释器，则提示配置解释器后重跑，不让用户误以为登录代码有错。

## 4. 功能与验收条件

P0 是引导体验的上线门槛，P1 是上线后的便利性提升。每项由可观察行为验收，不以「模型说已完成」验收。

| 编号／优先级           | 产品要求                                                                           | 可验收的行为                                                                                                       |
| ---------------------- | ---------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| R1 · P0 需求录入       | 保留原文、来源和用户补充；区分明确要求、推断和可选建议                             | 宿主没有上下文时仍能靠粘贴完成全流程；有歧义时最多先问一个会改变判定的问题，也允许「暂不确定」                     |
| R2 · P0 本地发现       | 有界只读扫描变更附近的清单、测试文件和静态用例名；识别子项目及运行目录             | 扫描不导入项目模块、不运行收集命令、不安装依赖；两个子项目有同名测试时展示两者来源，不擅自选一个                   |
| R3 · P0 智能规划       | 用需求生成「前提／行为／预期结果」，再用本地清单约束模型输出                       | 每项引用一段需求；模型建议新范围时标为「额外建议」。不存在的文件、用例、动态生成而无法辨认的用例均不可展示为已匹配 |
| R4 · P0 人工编辑       | 允许增删改、换候选、改为人工；提供原文与确认范围的对照                             | 删除原始必需项须明确显示为排除；重新打开草稿保留人工修改；重新生成只展示差异而不静默覆盖                           |
| R5 · P0 集中确认       | 编译为可审阅的本地执行计划；授权绑定项目、计划版本、命令参数、目录和选择的测试     | 拒绝、取消、非交互未授权或待执行计划已变，均不得启动测试；已有 DSH 宿主策略仍可否决用户侧请求                      |
| R6 · P0 执行反馈       | 显示当前条件、进度、耗时、取消入口；复用已有命令和 JUnit 执行链                    | 缺解释器或超时给出 `ERROR` 及恢复动作；已启动的任务如实记录。用户取消不再启动后续任务，不把未执行项标为通过        |
| R7 · P0 可解释报告     | 首页只展示范围、结论、阻塞项和下一步；二级展开原文、方法、目标测试、证据编号／路径 | 同一运行在 CLI、DSH、Markdown、JSON 显示相同状态与计数；不依赖颜色传递状态；日志可展开但不淹没结论                 |
| R8 · P0 手动与离线路径 | 无模型、拒绝外发、模型超时或输出无效，都可继续手工规划；保留现有配置入口           | 不需要 API Key 即可编辑计划、绑定测试、授权运行、看报告；回退时说明是规则或人工草稿，不伪称 AI 已分析              |
| R9 · P1 复验与交接     | 支持只重跑问题项、展示与上次变化、复制最小返工摘要                                 | 每次复验有新运行编号；旧的通过证据不自动并入新快照，部分复验不冒充全量通过；交接须由用户主动复制或发送             |

**怎么选测试。** 优先采用用户已绑定的目标，其次是候选中同时有相关断言与文件／模块关联的测试。只有名字相似时写「可能相关，请确认」，列出理由；遇到同名、找不到断言、只找到构建脚本时保留缺口。不展示未经校准的「置信度 97%」。即使测试匹配，也应允许用户指出「这个断言并没有验证我的要求」。

**首批适配。** Node 优先 `node:test`；Python 优先已有 `unittest`，项目已有 pytest 时支持具名 JUnit 结果。真正可判定的普通命令仍可手工约定；如果当前环境只能取得泛化的成功退出码，就展示进程证据，不自动提升为业务结论。无法静态发现的其他框架、参数化测试可手工绑定或待复核；不为完成引导强制安装框架。

**人工核对也是一条完整路径。** 对「弱密码有清晰提示」，可以建议：「用不符合项目密码规则的输入尝试注册；确认页面说明了哪条规则未满足，并确认账户没有创建。」用户可记下观察、关联条件和本次运行，也可以写「接受此缺口」及原因。界面并列展示「机器：未验证」「人工：已核对／接受缺口」；刷新、导出或复验都不能把人工备注变为机器 `PASS`。若项目没有规定密码规则，先问清规则，不自行规定长度。

## 5. 什么证据能得出什么结论

**计划、执行、签收是三件事。** 草稿只用「找到候选／待确认／无可用检查」，运行中只用「等待／运行中」。以下四种词只属于验收结果；「用户决定接受」是单独的人工决定，不回写机器结果。

| 结果                   | 足以给出该结果的例子                                                                                     | 报告应该引导用户做什么                                       |
| ---------------------- | -------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `PASS` 已验证          | 本次运行唯一选中的具名测试确实执行并通过，且运行完整；或显式工具条件「类型检查成功」履行已确认的命令契约 | 看清通过的是哪个行为、用的什么证据，而不是「整个产品没问题」 |
| `FAIL` 不符合          | 与条件相关的断言明确失败；或已完成的检查明确违反其约定                                                   | 展示预期、实际及证据入口；可复制给开发者                     |
| `UNVERIFIED` 证据不足  | 没有相关测试、匹配不唯一、目标被跳过、仅构建成功，或需要的输出可能被截断                                 | 指出具体缺口；允许绑定已有测试或照步骤人工核对               |
| `ERROR` 检查未正常完成 | 无法启动、超时、必要报告损坏、测试环境或设置出错                                                         | 先修环境或检查方法，再重跑；不要归咎于产品逻辑               |

**总体结论。** 引导模式仅在非空的已确认范围全部通过、工作区稳定且无阻塞性 Git 状态时显示 `VERIFIED`。任一必需项无证据、运行未完成或只复验一部分，均不对整项交付报绿。如果用户显式排除了原始要求，允许显示「已选范围全部通过」，但必须同时列出排除项，不能写「原始需求全部满足」。不同粒度分别标注：机器字段表达确认范围，交付摘要说明原始范围的缺口。

**证据链。** 从原始需求片段 → 条件 ID → 已批准计划版本 → 命令或测试选择器 → 本次运行及证据 ID → 原始记录，可逐步追溯。报告区分目标断言、工具检查和人工备注。具名测试的异常、缺失与冲突按[既有判定契约](configuration.md#junit-checks)处理，不新设一套模型评分规则。预检失败或中途取消若无法形成完整报告，只显示真实运行状态和已有记录，不制造证据。

## 6. 信任、隐私与易用性底线

- **先本地，后可选外发。** 默认不发源码、diff、日志或会话。可使用宿主已配置且授权的模型、用户配置的本地模型，或无模型模式。选择远程模型前显示提供方、将发送的具体字段与文件片段，允许删减；默认只建议发送需求和必要的候选描述。不同意则回到本地模式。DSH 自身已有的对话传输与 DoneGauge 新增读取、发送的材料须分别说明。
- **规划不获得执行权。** 仓库文本、测试名、模型输出都是数据。本地发现产出带来源的候选，模型只引用候选 ID；意外的命令、依赖安装、下载脚本、提权或仓库外路径不得进入引导模式的可执行计划。用户手工绑定的程序要单独标明来源。允许列表不是沙箱：测试代码仍按本机用户权限运行，可能写文件或联网。
- **保护工作区和批准。** 默认草稿、批准摘要与结果留在本地保留目录，不覆盖现有配置、不暂存、不提交；导出配置须用户主动操作。计划、项目或候选测试内容发生影响执行的变化时要求重新审阅；执行中的变化用快照披露。执行批准不是对后续任意命令、代码或外发的永久许可。
- **给拒绝和失败留出口。** 授权拒绝后可返回草稿；网络失败不影响已有本地检查；日志截断展示截断原因。报告和草稿可包含敏感信息，提供本地存放位置；复制交接摘要前先预览，不默认带完整命令输出、绝对路径、源码或环境变量。
- **初学者和自动化不互相妨碍。** 首屏先说人话，再提供技术详情；支持纯键盘、无颜色终端和长路径。非交互环境绝不等待隐藏提示或默认同意；没有明确批准只输出草稿与下一步。当前 `check`、配置 v1、报告 v1 与退出码保持兼容；引导计划独立版本化，不给原报告重新解释含义。

## 7. 交互与工程边界

| 层             | 拥有的职责                                                         | 不允许做的事                                   |
| -------------- | ------------------------------------------------------------------ | ---------------------------------------------- |
| 上下文发现     | 本地原文、项目范围、候选测试与来源；对子项目和过大目录说明跳过原因 | 加载仓库代码、后台上传完整项目                 |
| 规划与编辑     | 生成可保存的草稿，关联需求、条件、候选测试；保留人工改动与排除项   | 赋予 PASS、直接提交命令给执行器                |
| 审阅与批准     | 展示可读范围及准确参数；生成绑定当前项目与计划摘要的本次许可       | 用模型输出或旧计划的批准代替人的批准           |
| 执行与判定     | 复用现有 core 执行和采证；对批准摘要、工作区及证据完整性做检查     | 根据模型措辞提升状态，或从旧报告借用本次证据   |
| CLI／DSH／报告 | 让两种入口消费同一计划和结果；DSH 只返回必要摘要，原始证据留在本地 | 给现有无参数执行工具添加任意命令或项目路径参数 |

**DSH 交付条件。** 先验证宿主能否取得用户明确选择的任务文本，以及能否承载可信的人类确认。若前者不可用，用粘贴；若后者不可用，可从 DSH 打开本地 CLI 完成审阅，再返回结果。两端使用相同的计划摘要，不增设第二轮逐项批准。宿主额外要求的权限策略仍生效。未完成真实宿主演练前，不宣称已有原生一键流程。

**本轮不做：** 自动修复、自动生成并运行新测试、完整安全审计、多 Agent 调度、云账号和管理后台、强制付费模型、任意语言自动适配。更多 Agent 接口、测试草案、历史趋势和 CI 产品化保留在后续路线图；不阻塞这次体验改版。

## 8. 全面优化计划

按依赖排期，不先承诺日历日期。每阶段交付一条用户能实际走通的路径；门槛未过则停在该阶段，不用下一阶段的界面掩盖证据缺口。

| 阶段                | 要交付的最小切片                                                                                             | 依赖与完成门槛                                                                                                    |
| ------------------- | ------------------------------------------------------------------------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| M0 · 锁定基线与原型 | 用已有注册／购物车示例记录当前流程；画出录入、审阅、报告三个视图；定义条件、候选、草稿、批准、证据的数据关系 | 无前置。回放 v1 配置、报告、退出码和 DSH 工具；为每个明确要求标注可接受的测试及不相关的干扰用例                   |
| M1 · 无模型即可走通 | `review` 的本地发现、规则草稿、人工增删改、一次批准、执行及缺口报告；不改动已有 `check`                      | 依赖 M0。首次用户在 Node 和 Python 示例上不用写 JSON 均能完成；拒绝、无测试和无模型三种分支有明确出口             |
| M2 · 让建议真正有用 | 接入首个可替换的规划提供方；实现外发预览、证据来源、歧义提问、候选校验、回退与草稿差异                       | 依赖 M1。用人工标注任务检查覆盖与误配；伪造候选、超时、无密钥、拒绝外发都不启动测试、不丢人工修改                 |
| M3 · DSH 与发布验收 | 补齐 DSH 上下文／确认能力探测，接入同一审阅和证据视图；完成新手走查、兼容、安装和隐私检查                    | 依赖 M1/M2；宿主能力探测可在 M0 先做。真实 CLI 与 DSH 分别演练通过、失败、拒绝、取消；明确记录原生与 CLI 回退路径 |
| M4 · 发布后 P1      | 只复验问题项、跨次差异、可选交接模板；依试用中最常见的阻塞再决定支持哪个框架                                 | 仅在 P0 门槛通过后做。旧结果不得变成本次通过证据；不能用更多功能替代首次使用改进                                  |

**主要交付风险。** 若模型误配测试，收紧到可引用的本地候选，而非换一个更自信的提示词；若 DSH 无法可靠确认，发布诚实的 CLI 接续体验，而非放宽权限；若大仓库扫描过慢，先限定子项目、设扫描预算并披露遗漏，而非后台无限扫描。

## 9. 如何判断这次改版值得发布

以下均为**建议验收目标，不是实测成绩**。M0 先测基线；任一信任底线失败，都不以速度或满意度抵消。

| 维度             | 测量办法                                                                                                 | 首轮放行门槛                                                                                                      |
| ---------------- | -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------- |
| 不误报、不越权   | 固定反例：构建成功但无目标测试、同名误配、全跳过、旧 JUnit、未批准或批准后改计划、拒绝远程模型           | 反例中业务项错误 PASS 为 0；未授权测试进程为 0；拒绝后新增外发请求为 0                                            |
| 建议质量         | 至少 20 个脱敏或示例任务，Node/Python 各半；人工标注明确要求、已有匹配和故意缺失项，留出不参与调优的任务 | 明确要求被保留为条件或缺口的比例 ≥90%；推荐为可直接绑定的候选中，人工确认相关的比例 ≥90%；两项分别报分子分母      |
| 首次使用         | 5 名未使用过 DoneGauge 的目标用户，在依赖已就绪的示例中从粘贴需求开始，无研究员代操作                    | 至少 4 人在 3 分钟内审阅并启动首轮检查，且能正确指出混合报告里哪项未验证、下一步做什么；记录卡住的界面            |
| 发现耗时与透明度 | 固定设备、1 万文件受控仓库，排除依赖与构建目录；记录至少 20 次本地冷启动，不含模型和测试耗时             | 首次候选列表 P95 ≤5 秒；达到扫描预算后仍返回可编辑草稿，并标出未扫描范围                                          |
| 可复现和兼容     | 在两个示例及仓库已有 CI 矩阵中验证打包安装、原有 v1 调用及新 CLI 路径；另记录真实 DSH 宿主版本和操作轨迹 | 凡声称支持的路径均须有实际结果；CLI／DSH 的同一运行摘要能对上磁盘证据。截图、模型复述和模拟工具调用不能单独算通过 |

**端到端演示脚本（发布前必跑）：**

1. **Node 注册。** 从自然语言生成前三条已有目标，再加入无现成测试的弱密码提示；用户修改一项后集中批准。三条目标真实通过、第四条为 `UNVERIFIED` 时总览不得全绿。随后在临时副本引入登录回归，报告必须能定位真实失败断言。
2. **Python 购物车。** 从「0.10 + 0.20 必须精确，负价格必须拒绝」出发，推荐具体方法；用户能看到对应的 `test_exact_total`、`test_negative_price`。在临时副本中破坏其中一项，再选择一个不存在的解释器，分别得到 `FAIL` 与 `ERROR`，页面给出不同下一步。
3. **信任与降级。** 分别拒绝远程发送、取消执行确认、批准后修改测试、运行中取消、只做人工核对。核对进程、发送记录与报告；拒绝后没有相应动作，未完成的事不写成已完成。原工作仓库不作演示性修改。

指标首先用本地计时、受控样例和自愿可用性走查收集，不为取数默认开启遥测。运行记录里出现的真实项目材料，未经用户选择不得用于评测集。

## 10. 评审需要拍板的三件事

1. **是否把 `review` 设为新手主入口？** 建议是；把 `check` 留给已有配置和自动化。两类用户都不必为另一类人的需求改变习惯。
2. **首发要不要依赖某一个模型？** 建议不依赖。先发布一个接好并实测的可选提供方和完整的无模型路径，不在首版做模型市场。
3. **哪些缺口宁可不自动化？** 建议明确保留三类：找不到直接行为证据、用户尚未澄清的需求、宿主无法可靠确认的执行。少给一个绿色结论，胜过给出一个无法解释的绿色结论。
