# DoneGauge 下一阶段实现方案

本文区分当前能力与拟议设计。**JUnit 检查器、Windows 完整支持、DSH 界面级测试和 npm 发布流水线均为待实现方案**，不能将下面的示例当作 V0.1 已支持的配置。V0.1 的真实验证记录见 [validation.md](validation.md)。

## 1. 建议顺序

| 顺序   | 工作                      | 可验收的产物                                                   |
| ------ | ------------------------- | -------------------------------------------------------------- |
| 已完成 | 公有 GitHub 仓库和真实 CI | MIT 源码、可复现构建、Ubuntu/macOS 的实际检查记录              |
| 再做   | JUnit 检查器              | 将验收条件关联到本次执行中的具体测试，识别跳过、零测试和旧报告 |
| 随后   | DSH 界面级验收            | 人工主动触发、模型实际工具调用、报告落盘、取消与权限拒绝记录   |
| 随后   | Windows 支持              | 进程树清理、可执行文件解析、路径处理及 Windows CI              |
| 发布前 | 发行流水线                | 校验过的安装包、校验和、GitHub Release；经单独授权后发布 npm   |

不增加云账户、管理后台或模型自动打分。当前 core、CLI、DSH 分层足以支持这些改动。

## 2. 怎样补齐 DSH 界面验证

当前测试已覆盖官方宿主加载和工具分发，但不能证明某个模型在实际对话中能看见、正确选择并使用该工具。

### 验收流程

1. 创建独立示例项目、独立 DSH profile 和配置覆盖文件，不修改日常 Desktop 配置。
2. 由人审阅 `donegauge.json`，绑定项目根目录和配置 SHA-256。
3. 先测试一个真实可用模型/配置，让用户发送固定请求：“请调用 donegauge_check，验收这个项目，并告诉我哪些条件缺少证据。”
4. 检查会话中真实的 `tool/call` 和 `tool/result`：名称、空参数、执行状态、证据 id 与文件路径必须一致。模型只说“已验证”不算成功。
5. 分别运行全通过、混合失败、配置摘要变化、策略拒绝、执行中取消五种场景。
6. 对照磁盘报告核验模型总结，记录宿主版本、模型标识、测试场景和结果；截图仅作辅助，不代替工具执行记录。

后续可通过官方 UI 测试入口和稳定的控件标识自动化。离线回放适合验证 UI 渲染和协议回归；“实时模型会选择工具”的结论仍应由真实模型调用支持。对话可能涉及付费 API 或已有登录态，因此应在实际执行前明确使用哪个模型和账户，不把这项检查加入每次普通 CI。

验收门槛：工具可见、确实被调用、四种领域状态呈现正确、取消后前台检查停止、拒绝或摘要不符时没有命令启动。自定义结果卡片可晚于这些验证。

## 3. CI 与开源发行

仓库已有 GitHub Actions。首次推送后，应等待 Ubuntu/macOS 的完整任务结束，并检查实际日志；不能以工作流文件存在代替通过。

短期保留 Node 24 完整测试；增加 Node 22 核心/CLI 兼容任务时应排除要求 Node 24.9+ 的 DSH 宿主测试。Windows 修复完成后再加入正式支持矩阵。

CI 必须包含：严格类型、静态检查、格式检查、真实 Node/Python 端到端测试，以及 npm tarball 的实际安装和可执行入口验证。打包安装测试采用 `--prefer-offline`，允许全新机器在缓存不足时下载依赖，避免仅在开发机缓存齐全时通过。

稳定后设置 `main` 必须通过这些检查，并通过 PR 合并；这是后续仓库规则设置，不在首轮建仓时假定已经启用。普通验证工作流只需只读仓库权限，不放发布令牌。

发行按三个步骤推进：

1. `npm pack` 后检查文件清单，排除本地证据、环境文件、个人配置和开发缓存；在干净项目中实际安装 tarball。
2. 经验证的版本可以单独创建 tag 和 GitHub Release，附安装包、SHA-256、变更说明和已知边界。
3. 需要 npm 分发时，先确认包名可用性与归属，再建立发行身份或可信发布流程。成功从公共 registry 安装并运行后，README 才改为 `npx donegauge` 快速安装。

本轮只创建公有源码仓库并运行 CI，不自动发布 npm 包，也不自动创建发行 tag。

## 4. Windows 的具体改造

不能简单将所有命令切换为 `shell: true`。这会改变参数和权限语义，重新引入 Shell 解释问题。

### 启动命令

保留参数数组。原生 `.exe` 使用 `spawn(..., { shell: false })`。Node/npm 工具优先使用明确的 JS 入口并由 Node 启动；若支持 `.cmd`/`.bat`，应提供用户显式选择的 Windows Shell 执行方式，并对该方式单独测试、单独展示实际启动命令。拒绝无法安全或明确解析的命令，并给出处理方法。

### 停止命令树

第一步可使用 `taskkill.exe /PID <pid> /T /F` 作为受测试的常规进程树清理方案，固定系统程序、验证 PID、分开传参，不拼接用户命令。不能把它描述成原子、无竞态的进程隔离。

长期若需要保证整个检查生命周期和清理，应采用受维护的 Job Object 方案：将进程及子进程归组、配置关闭时终止并保证句柄释放。这需要真实 Windows 验证，不为 V0.1 引入未经测试的原生组件。

### 文件系统和测试

将 Git 无索引比较中的 POSIX `/dev/null` 替换为平台支持的方式；检查盘符、大小写、UNC、中文与空格路径、CRLF、符号链接和 junction 的边界。不以一个平台的软链接测试通过推断另一个平台安全。

Windows CI 应覆盖：正常通过、断言失败、命令缺失、超时及后代进程、Ctrl+C/取消、日志截断、中文与空格路径、安装后的 CLI 入口和真实 Node/Python 示例。当前 POSIX 专属测试可以保留条件，但要提供对应 Windows 测试，不能用全部跳过来宣称兼容。

## 5. JUnit 检查器解决什么

当前通用检查器验证退出码和可选输出片段。这适合本地工具，也有明确边界：一个错误筛选器可能没有执行目标测试；目标测试可能被跳过；输出可能包含测试名字却没有真正通过；旧报告也可能残留。

JUnit XML 是许多测试工具可输出的交换格式，名称不意味着只支持 Java。Node 内置测试运行器和 pytest 都有官方输出方式。实现时应以当前真实输出建立兼容样例，因为不同工具和版本的具体结构并不完全一致。

目标是将链条补全：

```text
验收条件 -> 明确配置的命令 -> 本次生成的 JUnit 文件
         -> 被明确选中的 testcase -> 实际状态与失败信息
```

它仍然不能证明测试断言正确、覆盖充分，或测试代码没有伪造报告。它提供更具体、可复核的证据；需要更高可信度时，应结合人工审阅的测试、独立 CI 和固定版本来源。

### 本轮真实格式验证发现的一个陷阱

在本机 Node.js 24.16.0 上，注册示例正常执行时产生 3 条具名 testcase。将测试名筛选器改为一个不存在的名称后，命令仍退出 0，JUnit XML 中仍有 **1 条 testcase**，但它的名称只是测试文件路径，并不是任何目标断言，也没有 failure 标记。

因此，“XML 中 testcase 数量大于 0 且没有 failure”仍可能误判。判定必须检查被明确选择的业务测试名称，而不能把文件执行外壳、父 suite 或总数当成断言已经通过。实现时应保留这种真实格式的回归样例；原始实验文件保存在本地忽略目录，不作为产品已实现的证据。

## 6. 拟议配置：兼容已有 command 检查

以下为**尚未实现的配置提案**，当前 V0.1 的严格 Schema 会拒绝这些新字段：

```json
{
  "version": 1,
  "task": "Implement user registration",
  "criteria": [
    {
      "id": "duplicate-email",
      "description": "Duplicate email is rejected",
      "check": {
        "kind": "junit",
        "command": [
          "node",
          "--test",
          "--test-name-pattern=duplicate email",
          "--test-reporter=junit",
          "--test-reporter-destination={evidenceDir}/junit.xml",
          "registration.test.mjs"
        ],
        "junit": {
          "file": "{evidenceDir}/junit.xml",
          "tests": [{ "name": "duplicate email is rejected" }],
          "minExecuted": 1
        }
      }
    }
  ]
}
```

`kind` 缺省时继续使用现有 command 逻辑，保留既有配置行为。新增 JUnit 分支在 Schema 中独立验证，避免把不适用的命令输出约定与测试选择语义混用。旧版程序遇到新字段应明确报错，不能静默退回弱检查。

`{evidenceDir}` 是程序提供的固定占位符，替换为本次检查新建的专属目录。只替换这类已知占位符，再用 argv 启动程序，不启动 Shell，也不支持任意模板表达式。

测试选择先支持精确 `name` 和可选 `className`；同名不唯一时给出歧义提示并判 UNVERIFIED。参数化测试必须明确列出稳定名称；第一版不引入模糊搜索、复杂正则或“猜测最相关测试”。

## 7. 保证文件来自本次运行

1. 每条检查创建新的随机 id 和空的专属证据目录。
2. 在启动命令前确定唯一输出路径，不复用项目里已有的 `junit.xml`。
3. 命令结束后，仅接收该目录内的正常文件；检查路径包含关系、软链接和文件大小。
4. 保存原始 XML、SHA-256、运行 id、配置摘要、Git 基准和工作区指纹。
5. 将解析后的测试记录与同一次进程证据关联，报告同时保留 stdout/stderr 和退出状态。

不能只凭 mtime 判断新旧，也不能先删除用户已有文件再假装得到了新证据。只有导入旧 XML 的场景可单独标记为历史证据，默认不用于当前工作区的 PASS。

## 8. 解析与规范化

新增轻量模块，不引入通用测试平台：

```text
src/core/junit.ts          有界 XML 读取、解析和格式规范化
src/core/junit-evaluator.ts 精确选择、证据完整性和状态判定
src/core/types.ts          JUnit 配置与结构化测试证据
schema/donegauge.schema.json 新增检查分支
tests/junit.test.ts        格式、状态和边界测试
tests/junit-e2e.test.ts    真实 Node / pytest 报告
```

统一记录：suite、className、name、file/line（存在时）、duration、outcome、失败类型/信息/堆栈，以及原始文件位置。报告中明确“测试文件位置”和“疑似产品代码位置”的区别，不把堆栈第一行直接认定为根因。

解析器支持 `<testsuite>` 与 `<testsuites>`、嵌套 suite、`failure`、`error`、`skipped`、CDATA 与常见属性。按叶级 testcase 统计，避免把父级 suite 重复计数。不只相信 suite 上声明的 `tests` 数字。

使用维护中的 XML 解析库，禁用 DTD、外部实体和外部资源访问；限制文件大小、嵌套和 case 数量。初始可采用 10 MiB、50 层和 50000 条 case 作为有文档的上限，实际实现需经过内存与性能验证后固定。

重复名称、相互矛盾的状态、非有限时长、统计不一致和不支持的重试标记都应明确呈现。失败后重试通过不能静默抹掉第一次失败；第一版可保守要求复核，而不是实现复杂 flaky 策略。

## 9. 判定规则

| 本次运行的实际证据                                                              | 验收状态   |
| ------------------------------------------------------------------------------- | ---------- |
| 所有指定测试均唯一匹配、真实执行并通过，达到最低数量，命令正常退出 0，证据完整  | PASS       |
| 指定测试含明确 assertion failure                                                | FAIL       |
| 没有 testcase、指定测试不存在、被 skip/todo、匹配有歧义，或证据不是本次生成     | UNVERIFIED |
| 命令无法启动/超时/取消、XML 缺失或损坏、测试 setup/teardown error、输出状态矛盾 | ERROR      |

命令非零不应把所有测试统一改成 FAIL。先保存完整进程状态，再解释有效的测试报告；有明确失败记录时可给出具体 FAIL。若目标 case 都通过但进程非零，第一版保守标记为运行与结果冲突的 ERROR，并展示目标 case 的通过记录，避免声称整条检查成功。

同一条件存在多条目标记录时，优先显示执行错误，其次明确失败，然后是缺失或跳过；只有全部满足约定才 PASS。报告应列出各条记录，不能只保留最高优先级的总状态。源代码在运行中变化时，仍沿用当前整体 REVIEW REQUIRED 规则。

## 10. 报告与测试

保持终端简洁，增加测试名、执行数量与证据路径；Markdown 增加目标测试表和失败详情；JSON 增加可选 `testEvidence`，记录原始文件哈希、解析器版本、匹配规则、数量和每条结果。只做增量字段扩展时可保留 `reportVersion: 1`，出现破坏性变化才升级格式版本。

第一阶段仍采用每个条件配置一条明确命令，避免立即增加跨条件执行缓存。确有重复执行成本后，再增加命名检查与结果复用；同一次执行可以被多个条件引用，但必须保持同一份证据 id。

必须实际验证：

- 真正通过与真正失败的 Node/pytest 项目。
- exit 0 但零测试、全部 skip、目标名字拼错、只运行了不相关测试。
- 旧报告残留、命令未生成文件、报告为空/损坏/过大、路径越界和软链接。
- 子测试嵌套、参数化名称、重复名称、失败后重试、缺少 file/line。
- XML 明确失败但进程退出 0，以及目标通过但进程非零。
- 超时后残留的部分 XML 不得产生 PASS。
- 三种报告与 DSH 返回的状态、测试数量、证据 id 一致。

构造 XML 可用于解析器单元测试，但验收示例和端到端报告必须由真实测试命令产生。JUnit 第一阶段的完成标准，是这些场景实际通过，且已有 command 配置与 V0.1 的行为保持兼容。
